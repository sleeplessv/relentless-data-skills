01The catalogue at a glanceTable 1

The catalogue is 18 skill folders under skills/, each with a SKILL.md and a plugin.json. Table 1 lists them. SKILL.md length stays in a narrow band, 56 to 150 lines. Script count ranges from 0 to 17.

@@TABLE1@@

Table 1. Every skill folder with its version, SKILL.md length, file counts, commits and tracked size. Each bar is that SKILL.md's share of the 150-line budget. Coral cells sit exactly on it. DMI means disable-model-invocation: true. A commit that touches several skills counts once per skill, so Commits sums to 210, not 124. Click a header to sort.

So whatThe budget caps the prompt, not the skill. Folder size comes from scripts.

  • Eight of 18 skills set DMI. The linter requires it for any skill that runs git push or gh pr merge.
  • Five SKILL.md files sit on the budget. None is over it.

02The 150-line budgetFigure 1

scripts/lint_skill.py sets LINE_BUDGET = 150 on line 35 and fails any longer SKILL.md. CI's skill-lint job runs it on every push and pull request. Detail that does not fit goes in references/, which the agent reads only when SKILL.md sends it there. Figure 1 shows every SKILL.md against the budget.

Figure 1. SKILL.md length per skill, longest first. The dashed line is the 150-line budget. Coral bars sit exactly on it. Mean 127.3 lines, minimum 56 (visual-report).

So whatFive skills are at the limit and two more are within 3 lines of it. The budget binds.

  • The most-touched folders are orchestrator-mode (25 commits), snowman (23) and implement-ticket (22).

05How the render check runsFigure 4

check_render.py opens a report in headless Chromium and reads the rendered page, not the console. It records diagram facts, opens hidden tabs and <details>, then records them again. Each diagram ends as ok or one of eight faults, such as clipped or illegible. The run stops at 140 s. Figure 4 follows one run.

@@SEQ@@

Figure 4. One run of check_render.py, from the agent's command to the verdict. Solid arrows are calls. Dashed arrows are replies. Each alt box runs only when its condition holds. The script's 17 steps are condensed to 12 messages.

So whatAn unrendered diagram counts as a defect only after a CDN probe clears the network.

06How the verdict is decidedFigures 5 and 6

verdict() checks four tiers in order and returns at the first match (Figure 5). Figure 6 gives the verdict for each condition on its own. Exit codes are PASS 0, FAIL 1 and BLOCKED 2.

Note. SKILL.md defines BLOCKED as "unverified, not passing".

@@CODE@@
  1. 1361 blocked means the check never ran, so it wins outright.
  2. 2365 A DRAWN_BAD status proves a defect, unless the diagram's module never loaded.
  3. 3367 A broken image or a frozen tab fails with no network excuse.
  4. 4369-370 An unreachable CDN or a timeout gives BLOCKED.
  5. 5372 Unrendered diagrams and console errors fail only when the network was fine.

Figure 5. verdict(), lines 354 to 375 of skills/visual-report/scripts/check_render.py. Line numbers match the source. Numbered markers point to the notes under the code.

So whatThe order is the design. A network fault never becomes a page defect.

@@MATRIX@@

Figure 6. Each condition from the script's docstring and the verdict it gives on its own. ✕ is FAIL, ◆ is BLOCKED and ● is PASS. When several conditions hold, the order in Figure 5 decides.

So whatOnly three conditions end in BLOCKED, and the environment causes all three.

  • A drawn defect fails. An environment fault blocks. Softer evidence fails only when the network was fine.

07How visual-report got its checkFigures 7 and 8

skills/visual-report/ has 12 commits on main. Ten are prose passes across many skills. Commit 088a29f added the render check and its tests (Figure 7). The same commit rewrote the Verify step in SKILL.md to run it (Figure 8).

@@TIMELINE@@

Figure 7. Every commit that touched skills/visual-report/, oldest first. The highlighted entry, 088a29f, added check_render.py and tests/test_visual_report.py.

So whatThe check arrived four months after the skill, in one pull request.

@@DIFF@@
  1. 1-36 Before: re-read the Mermaid blocks and look at the page yourself.
  2. 2+39 After: run check_render.py on the report.
  3. 3+44 FAIL: fix each problem and rerun.
  4. 4+45 BLOCKED counts as unverified, never as a pass.
  5. 5+46 PASS still needs every screenshot read.

Figure 8. The Verify step of skills/visual-report/SKILL.md, before and after commit 088a29f. Red lines were removed, green lines added. The darker tint marks the changed words. The left column numbers the old file, the right column the new.

09LimitsWhat this report cannot show

  1. Commit counts include merges and count a multi-skill commit once per skill.
  2. Graph edges come from grep and imports, not from run-time traces.
  3. Tracked lines count every file with wc -l, so binary assets count as almost zero.
  4. Figure 4 was read from the source, not traced from a live run.
