1. Eighteen skills, one line budget

The catalogue is 18 skill folders under skills/. Each folder has a plugin.json manifest that carries the version, a SKILL.md that the agent loads whenever the skill triggers, and, where the skill needs them, references/ and scripts/ subfolders. Table 1 lists all 18 with the measures this report uses. Click any header to sort.

Skill.
An independently versioned bundle of agent instructions and supporting files. Its documentation belongs to the same bundle.
Skill update.
A set of changes delivered together to one skill. Documentation corrections count as updates, even when the skill's behavior stays the same.
Skill version.
The identifier of a skill revision, used to track changes and support updates to installed copies.

The SKILL.md column is nearly flat, 56 to 150, while the scripts and commits columns are not. The budget shapes the prompt, not the skill.

scripts/lint_skill.py sets LINE_BUDGET = 150 on line 35 and fails any SKILL.md above it with the message "SKILL.md is N lines (budget 150)" on line 160. The CI job skill-lint runs the linter on every push and pull request, and scripts/check.sh runs it locally. The comment on lines 32 to 34 calls the budget "deliberately stricter than the docs' 500-line guidance", so that detail moves into references/. Figure 1 shows how hard that ceiling presses.

Five skills sit exactly on the budget and two more are within three lines of it. The ceiling is load-bearing, not nominal.

The mean is 127.3 lines and the shortest SKILL.md is 56 lines, visual-report. Only three skills are under 90 lines, fabric-lineage-dag (89), statusline (64) and visual-report (56), and each of the three keeps a scripts/ folder. The linter also decides who may invoke a skill. A skill whose files contain a command that acts on shared state, such as gh pr merge or git push, must set disable-model-invocation: true or be allow-listed with a reason. Eight of the 18 skills carry the flag.

Takeaways

  1. All 18 SKILL.md files are at or under the 150-line budget, five sit exactly on it, and the mean is 127 lines. The linter that enforces the budget runs on every push and pull request.
  2. Eight of 18 skills carry disable-model-invocation: true. The linter forces it onto any skill whose files run a shared-state command such as git push or gh pr merge.

4. How the render check runs

The visual-report skill verifies a report with check_render.py, 985 lines, invoked as uv run --no-project --with playwright python <skill-dir>/scripts/check_render.py <report.html>. It opens the report in headless Chromium through Playwright and prints PASS, FAIL or BLOCKED. Figure 4 follows one run from the agent's command to the verdict line.

The script never trusts the console. It reads the rendered DOM twice, re-renders suspect diagrams offscreen, and asks a known-good CDN URL whether the network is to blame before it lets an unrendered diagram count as a defect.

The two DOM reads bracket a reveal step. The first facts() snapshot records the diagrams as the page first shows them. Then __vrCheck.reveal() opens tabs, toggles and <details> as a reader would, the script waits for Mermaid to settle again, and the second snapshot records what appeared. A diagram that is still hidden after the reveal is listed as unverified, not judged. For up to 20 diagrams whose status is error, empty or lazy, or ok but drawn while hidden, the script re-renders the source offscreen with the page's own Mermaid module and attaches Mermaid's error text, or sets env when the probe shows the module never loaded.

5. How the render check decides

verdict() is 22 lines, lines 354 to 375 of check_render.py. Figure 5 shows the whole function with five markers on the lines that carry the decision.

The ordering is the design. An unreachable CDN explains an unrendered diagram, so the script refuses to call that a page defect.

Figure 6 lists the conditions the module docstring names (lines 2 to 25) and the verdict each produces on its own.

Only three rows end in BLOCKED, and all three are the environment's fault. That is why SKILL.md says "BLOCKED means unverified, not passing".

Row 8 becomes BLOCKED, not FAIL, when row 11 also holds. That is the point of the ladder: an unrendered diagram next to an unreachable CDN is a fact about the network, and the script says so instead of blaming the page.

Takeaways

  1. verdict() decides in 22 lines with a fixed precedence. A drawn defect, 404, broken image or frozen tab is FAIL. An unreachable CDN, missing browser or timed-out check is BLOCKED. An unrendered block or console error is FAIL only when the network was fine.

6. When the render check arrived

The visual-report folder has 12 commits in all, so Figure 7 is its whole history. The skill arrived on 2026-06-09 and the next nine commits are prose and style passes, most of them across the whole catalogue.

7. Where the lines live

Table 1 gave every folder's tracked lines. Figure 8 ranks the ten largest as shares of the 17,001-line catalogue, counting every git-tracked file: SKILL.md, README, plugin.json, references, scripts and assets.

Line count follows scripts, not prose. The four largest folders are the four with the most script code, while the most-committed skill, orchestrator-mode with 25 commits, is only 306 lines.

This is the claim at the top of the report in one picture. fabric-lineage-dag's SKILL.md is 89 lines, well under the budget, and its folder is 3,635 lines because its 17 scripts live there. The budget keeps the prompt short and lets the folder grow where the work is.

Takeaways

  1. Script code, not prompt text, is where the catalogue's bulk lives. fabric-lineage-dag's 17 scripts make its folder 3,635 lines, 21% of the 17,001 tracked lines, with an 89-line SKILL.md.

8. Limits

  1. Commit counts include the 5 merge commits, and a commit that touches several skill folders is counted once per folder, so Table 1's commits column sums to 210, not 124.
  2. Skill-to-skill and test-to-skill edges in Figure 3 are grep- and import-based. A skill name that appears in prose counts as an edge, and nothing here verifies that the dependency is exercised at run time.
  3. "Tracked lines" counts every git-tracked file in a folder with wc -l, including README and plugin.json, and treats binary assets (statusline's screenshots) as zero or a few lines.
  4. The sequence in Figure 4 was read from the source, not traced from a live run. No report was rendered to produce this content, and the CI job list reflects ci.yml at commit a590a62 only.
