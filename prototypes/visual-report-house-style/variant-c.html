1Eighteen skills, one table

A skill is an independently versioned bundle of agent instructions and supporting files. Each one is a folder under skills/ with a SKILL.md that loads whenever the skill runs, plus optional references/ and scripts/ that load on demand. Table 1 lists every folder with the measures the rest of this report uses.

The SKILL.md column is nearly flat, 56 to 150 lines, while the scripts and commits columns are not. The budget shapes the prompt, not the skill.

  • Eight of 18 skills set disable-model-invocation: true. The linter forces it onto any skill whose files run a shared-state command such as git push or gh pr merge.
  • Six skills keep no references/ files and ten keep no scripts/ files.
  • The commits column sums to 210, not the repo's 124, because a commit that touches several folders counts once per folder.

2Every SKILL.md fits the budget

scripts/lint_skill.py fails any SKILL.md over 150 lines, and the CI job skill-lint runs it on every push and pull request. Figure 1 puts every skill against that line.

Five skills sit exactly on the budget and two more are within 3 lines of it. The ceiling is load-bearing, not nominal.

  • The mean is 127.3 lines. The shortest SKILL.md is visual-report at 56 lines.
  • Seven skills are within 5 lines of the budget.
  • The source comment on lines 32 to 34 calls the budget "deliberately stricter than the docs' 500-line guidance", so that detail moves into references/.

6One run of the render check

check_render.py is the visual-report skill's verify step: 985 lines, invoked as uv run --no-project --with playwright python <skill-dir>/scripts/check_render.py <report.html>. Figure 4 follows one run from the agent's command to the verdict line, across five participants.

The script never trusts the console. It reads the rendered DOM twice, re-renders suspect diagrams offscreen, and asks a known-good CDN URL whether the network is to blame before it lets an unrendered diagram count as a defect.

  • The timings are constants at the top of the file: LOAD_TIMEOUT_S 30, QUIET_MS 2000, CALL_TIMEOUT_S 10, PROBE_TIMEOUT_S 15, and a default --timeout of 20.
  • The overall limit is 30 + 20 + 90 = 140 s. A watchdog thread fires at 160 s.
  • settle() waits until Mermaid's output is unchanged for 2,000 ms and gives up after 20 s with a warning.
  • Up to 20 suspect diagrams are re-rendered offscreen with the page's own Mermaid module, 15 s each.

7Where the verdict is decided

verdict() is 22 lines, 354 to 375 of check_render.py. Figure 5 shows the whole function with its four decisions marked.

The ordering is the design. An unreachable CDN explains an unrendered diagram, so the script refuses to call that a page defect.

  • The four if blocks are a precedence ladder. The first one that matches wins.
  • DRAWN_BAD is error, empty, illegible and clipped. NOT_DRAWN is unrendered and rendering.
  • Exit codes are PASS 0, FAIL 1, BLOCKED 2. Labels under 6 px make a diagram illegible; under 9 px they only warn.

8Which condition gives which verdict

The script's module docstring (lines 2 to 25) names the conditions it judges. Figure 6 maps each one to the verdict it produces on its own.

Only three rows end in BLOCKED, and all three are the environment's fault. That is why SKILL.md says "BLOCKED means unverified, not passing".

  • Rows 1 to 7 are the defect tier. Any one of them beats BLOCKED.
  • Rows 8 and 9 are the soft tier. BLOCKED beats them.
  • Row 8 becomes BLOCKED, not FAIL, when row 11 also holds. That is the point of the ladder in Figure 5.
